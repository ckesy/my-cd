
## 路线管理入口消失（模块闸门口径不一致）

**现象**：左侧「运输管理」里没有「路线管理」，但直接敲 `/route/manage` 能正常进、数据都在。

**根因**：beta49（b77c0a2）把菜单项从 `v-if="hasPerm('route')"` 改成 `v-if="routeOn"`，
`routeOn = moduleFlags.route === true`。而 `tenant_modules` 里老客户根本没 route 记录 →
`foldDeps` 按 defaultOn 兜底为 false（只有运单默认开）→ 菜单消失。
但 Dashboard 闸门 `isPermitted` 对主账号 `clientPerms===null` 直接 return true，页面照进。
两边口径不一致 = 「功能在、入口没了」。

**修复**（3 个文件）：
1. `src/utils/modules.js` 新增 `moduleHidden(key)`：库里**明确** `enabled=false` 才算关；
   没配过（intent 里没这个 key）返回 false，交给人级权限决定。与 `effective` 的语义差异写进注释。
2. `src/components/SidebarMenu.vue`：`routeOn/reportOn = isMaster || !moduleHidden(key)`。
3. `src/views/Dashboard.vue`：`MODULE_GATE` 判定改 `moduleHidden(gate)`；
   删掉 `'/fee/payout': 'payout'` 这条（下面有专门分支，避免口径分叉）。

**教训**：模块开关默认关 + 页面闸门对主账号放行，是这类「入口消失」的固定组合。
以后菜单写模块条件一律用 `moduleHidden`，别再直接判 `moduleFlags.x === true`。

## 静态托管缓存被网关掐死 → 上 Service Worker

**实测结论**：`webapps.tcloudbase.com` 与 `tcloudbaseapp.com` 两个默认域名，所有响应（含
`/assets/*.js`）都被 `tcbgw` 网关注入 `cache-control: no-store, no-cache, must-revalidate,
max-age=0` + `expires: 0` + `pragma: no-cache` + `content-disposition: attachment`，
且**没有 `content-encoding`（不压缩）**。控制台「基础配置」只有域名/索引文档/路由，
**没有缓存配置入口**。首屏实际传输 2.5MB 未压缩。

**方案**（不换托管）：`public/sw.js` 手写 SW，两条策略——
① `/assets/*` CacheFirst（文件名带 hash，永不取错）；
② 页面导航 NetworkFirst（index.html 永远最新 → **用户不需要点刷新、不用清缓存**，
下次打开自动是新版）。

**文件**：`public/sw.js`（新增）、`src/utils/swRegister.js`（新增，仅 PROD 注册、
`localStorage.sw_off='1'` 可一键停用+清缓存）、`src/main.js` 末尾调用。

**待线上验证**：部署后 `curl -sI https://域名/sw.js` 必须是 `content-type: text/javascript`，
若被网关注成 attachment/octet-stream 则 SW 注册失败。

**权衡**：首次仍需下 2.5MB；停留在页面不刷新的用户仍是旧版（任何网站均如此）。
不装 vite-plugin-pwa（vite 8 兼容性未验证），不拆包（首屏该下的照样下，收益低）。

## 技术架构澄清（用户纠正后修订）

抽技术架构图时被用户纠正三处，均已核实：

1. **Web 端不直连数据库**。`src/utils/supabase.js` 是 `cloudbase.init({env,region})` + `app.rdb()`
   （@cloudbase/js-sdk），路径是 浏览器 → CloudBase → CloudBase 数据服务 → PostgreSQL。
   ⭐ 配套的 PostgreSQL **没有内网/公网 IP**，任何客户端都连不上，必须经 CloudBase 中转。
   文件名叫 supabase.js 纯历史遗留（最初想用 Supabase），不是真 Supabase —— 这是误解源头。
2. **云函数不止 7 个，共 15 个**。7 个只是 `deploy/cloudfunctions-20261020` 那次部署快照，
   漏了 `cloudfunctions/` 下 3 个定时任务 + 代码里 HTTP 直调的 5 个外部代理。
3. **云函数就是后端**（BaaS + FaaS）。说"没有独立后端服务"有歧义，准确说法是
   "没有常驻服务进程，后端由 15 个函数组成"。

技术栈事实：
- 运行时 Node.js 18.15（部分老函数 Node 16 及以下，没有全局 fetch，只能用 https 模块）
- CommonJS，`exports.main = async (event, context)`，**无框架**（不是 Express/Koa，无端口无路由）
- 依赖分两派：6 个业务函数 `dependencies: {}` 零依赖；3 个定时函数依赖 `@cloudbase/node-sdk ^3.2.0`
- 数据访问不引 ORM，自建 HTTPS 打 CloudBase 数据接口（PostgREST 风格 URL + token 缓存）
- 三路触发：小程序 callFunction / HTTP 访问服务（函数型 URL）/ 定时触发器 cron
