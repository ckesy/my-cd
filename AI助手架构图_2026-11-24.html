00 · 设计前提
三条铁律

这三条决定了后面每一层的形态，先看它再看图。

法则 01

数字不过模型

所有数值由工具函数查库计算并直接渲染成卡片，模型只写解释性文字，禁止复述数字。避免大模型算错或改数。

法则 02

写操作只到草稿

派单、审批生成的是待确认的草稿，人工点击后才落库。AI 不代签、不自动提交，审计链完整。

法则 03

权限在服务端

无权限的工具根本不下发给模型，而不是靠提示词约束。即使模型被诱导尝试调用，也拿不到工具定义。

03 · 关键机制
两轮模型往返

这是本方案最核心的设计：第一轮模型只决定"查什么"，第二轮只负责"怎么说"。中间的数字由程序算好，模型碰不到。

轮 1 决定查什么 模型输出结构化参数，不产生任何文字回答
用户提问"上个月电耗最差的三个车" → 编排层附上可用工具描述 → 模型只返回工具名 + 参数 → 参数校验条数、日期跨度、枚举 → 执行工具强制注入租户条件 → 数据库返回行集
轮 2 决定怎么说 模型只写一句解释，数字已经在前端卡片里了
结果脱敏截断手机号打码、最多 20 行 → 模型只输出解释文字，禁止复述数字 → 写审计日志问题、工具、耗时、token 用量 → 返回前端答案文字 + 结构化卡片
为什么不干脆让模型直接答：如果让模型自己算「上个月电耗最差的三个车」， 它需要读取几十行数据再排序比较，算错的概率不低，而且错了没人发现。 现在的做法是：排序、汇总、排名全部在数据库里完成，模型只看到前三行结论。
04 · 工具层
四个白名单工具

工具是模型唯一能触达数据的通道，也是权限控制的实际执行者。

工具 能力 所需权限 数据范围 条数上限 说明
q_energy 能耗与里程 operation_energy 整队 50 行 读夜间已同步的日统计表，不实时聚合
q_fee 费用查询 fee_list 按身份自动收紧 100 行 主账号看全队，司机只看自己上报的
q_todo 待我处理 fee_list 整队 50 行 汇总待审批费用与待办运单
q_waybill 运单查询 waybill 按身份自动收紧 50 行 司机只能查自己的单，按账号过滤
数据范围那一列的差别是有意的：能耗看的是整队统计，司机本就没有这个权限入口； 而费用和运单两种角色都会用，所以工具内部按身份再收一次—— 同一个工具，主账号与司机执行出的 SQL 条件不同。
05 · 安全设计
四道闸门

从提问到返回，一共四道拦截。任何一道失效，都不会直接导致数据泄露。

闸 1工具不下发

无权限的工具不进入模型上下文。模型看不到这个工具，就不可能调用它。 这比"在提示词里说不要用"可靠得多。

闸 2参数白名单校验

工具名必须在白名单内，参数按 schema 校验类型与枚举， 日期跨度不超过 366 天、条数不超过上限，防止一次拉走全库。

闸 3身份由服务端注入

工具参数里不存在任何身份字段。租户与账号条件由编排层从会话中取出后强制拼接， 模型无法通过参数指定"查别人的数据"。

闸 4结果脱敏与截断

回填模型前，手机号与身份证正则打码，行数截断到 20 行。 即使模型被诱导复述，也拿不到完整的敏感数据。

控制项设定值作用
模型往返轮数最多 3 轮防止模型反复调用工具绕圈
单次提问工具调用最多 6 次防止同一次提问里重复查同一件事
请求硬超时15 秒超时直接中断，不让用户干等
输入 token 上限10,000超出则截断历史，控制成本
单账号配额60 次 / 小时防刷，同时控制调用成本
单租户配额800 次 / 天租户级总量保护
06 · 模型参数
能调哪些参数、怎么调

所有模型参数集中在同一个函数里构造，改一处即可生效。下面每一行都标了取值范围、默认值和本场景的建议。

当前代码实际传入的 6 个参数
位置：cloudfunctions/ai-gateway/llm.js 的 chat() 函数
参数当前值说明
modeldeepseek-flash官方现役只有 deepseek-flash 与 deepseek-v4-pro 两个，由环境变量 AI_MODEL 指定
messages系统提示 + 历史 + 用户问题历史超 token 上限会从最早的消息开始截断
temperature0.1偏低，适合"翻译成参数"这类确定性任务
max_tokens800输出上限。不设时默认 8K（非思考）/ 64K（思考），设 800 是主动省钱
streamfalse非流式，前端用逐字动画模拟

最后一轮 none		最后一轮强制不调工具，只允许输出文字，防止来回死循环
完整可调参数

按"影响什么"分四组。标「优先调整」的是建议先动的。

参数取值 / 默认作用本场景建议
thinking 优先调整 {type: enabled 或 disabled}
默认 enabled		 思考模式开关。开启后模型先推理再作答 建议设为 disabled。工具调用任务不需要推理，开启只会增加延迟和 token
reasoning_effort 优先调整 none / low / high / max
默认 high		 思考强度。none 等同关闭思考 与 thinking 二选一即可；用这个写 none 更简洁
temperature 0 – 2
默认 1		 随机性。越低越稳定、越可复现 保持 0.1。查数据要的是准确，不是文采
max_tokens 1 – 384K
默认 8K / 64K		 单次输出长度上限（含思考消耗） 保持 800。若开启思考模式需提高到 2000 以上，否则正文被思考挤掉
response_format {type:"json_object"}
或 text		 强制输出合法 JSON 不需要。本场景用工具调用输出结构化参数，比让模型吐 JSON 更可靠
stop 字符串数组 遇到指定字符串即停止生成 不建议。容易把解释截成半句话
tool_choice auto / none / required
或指定函数名		 是否允许调工具、必须调哪个 已用 auto + 末轮 none，这是正确用法，不要改成 required
top_p 0 – 1，默认 1 核采样范围，与 temperature 二选一调 保持默认。temperature 已经 0.1，两个一起压会让输出变得机械
frequency_penalty
presence_penalty		 -2 – 2，默认 0 抑制重复用词 / 鼓励新话题 不需要。输出只有一两句话，没有重复问题
logprobs
top_logprobs		 布尔 / 0 – 20 返回每个 token 的概率，用于置信度分析 过度设计。真要做置信度判断，不如用"工具是否命中"来判断
seed 整数 固定随机种子，让结果可复现 调试期可临时加，便于复现问题；生产不必
stream true / false 流式返回 保持 false。云函数对长连接支持不稳定，前端已用动画模拟
关于最后五个参数：top_p / stop / seed / 两个 penalty 属于 OpenAI 兼容字段，DeepSeek 接口大概率接受，但是否真正生效需要实测。 官方文档明确列出的是 temperature、max_tokens、response_format、 thinking、reasoning_effort、logprobs 这几个。
需确认 thinking 默认是开启的，当前代码没有关它

官方文档写明 thinking.type 默认为 enabled，而现有代码只传了 6 个参数，没有显式关闭思考。 如果实际按默认执行，会带来三个连锁影响：

延迟上升先推理再作答，15 秒硬超时可能不够，尤其第二轮
token 变多思考过程同样计费，配额消耗比预期快
输出被截断思考占用 max_tokens: 800 的额度，正文可能不够

验证方法：连续提问 10 次，对比改前改后的 latency_ms 与 completion_tokens（这两个值审计日志里都有）。若改后两项同时明显下降，说明之前确实走了思考模式。

怎么改：三步

参数分两处放，改动前先分清改哪一边。

环境变量不打包、随时改

在云函数配置页设置，改完重启实例即可生效，不用重新部署代码。
只有三个：DEEPSEEK_API_KEY、DEEPSEEK_BASE_URL、AI_MODEL。

代码常量要重新部署

在 llm.js 顶部：MAX_OUTPUT_TOKENS（输出上限）、 DEFAULT_TIMEOUT（单次超时）。改完必须重新部署云函数。

请求体要重新部署

在 chat() 里构造 body。绝大多数参数（thinking、temperature、 tool_choice 等）都在这里加。

改法与示例（llm.js 的 body 构造） 
// cloudfunctions/ai-gateway/llm.js — chat() 内
const body = {
  model: MODEL,
  messages,
  temperature: temperature == null ? 0.1 : temperature,
  max_tokens: MAX_OUTPUT_TOKENS,
  stream: false,

  // ← 新增：关闭思考模式（当前缺失，建议补上）
  thinking: { type: 'disabled' },

  // 或者用这个写法，二选一即可
  // reasoning_effort: 'none',
}
if (tools && tools.length) {
  body.tools = tools
  body.tool_choice = toolChoice || 'auto'
}
改动后执行部署，然后在审计日志里观察 latency_ms 与 completion_tokens 的变化。 不要一次改多个参数，否则分不清是哪个带来的效果。
按问题查参数

遇到具体问题时，从这里反查该动哪个。

遇到的问题调哪个怎么调
响应慢、经常接近超时thinking设为 disabled，或 reasoning_effort: 'none'
回答被截断、话没说完max_tokens从 800 提到 2000，同时确认思考模式已关
答案发散、爱自由发挥temperature已是最低档 0.1，再降意义不大；应从提示词入手约束
token 消耗太快、配额不够用max_tokens + thinking关思考、压输出上限；必要时下调历史轮数
模型该调工具却没调tool_choice临时改 required 验证，但不要长期用，会导致闲聊也强调查询
模型反复调同一个工具由上限控制已有 MAX_TOOL_CALLS: 6 兜底，无需调模型参数
想复现某次异常回答seed临时固定种子，复现后记得去掉
想换更强的模型model改环境变量 AI_MODEL 为 deepseek-v4-pro，重启即可，不用改代码
一句话原则：本场景的目标是把一句话准确地翻译成参数，不是让模型写得好看。 所以除了 thinking 该关、max_tokens 按需调之外， 其余参数保持默认就是最优解——每多调一个，就多一个说不清变量。
07 · 实现细节
数据结构与前端呈现

助手本身只新增两张表；前端不引入新框架，用现有能力做逐字动画与卡片渲染。

表关键字段用途
ai_sessions token、account、tenant、kind、expires_at 连接桥：Web 登录后签发，编排层只认这个令牌，不信任前端传来的账号
ai_assistant_logs trace_id、account_id、question、intent、tool_calls、tokens、latency_ms 审计 + 配额 + 成本核算三合一。问题文本脱敏后存，最长 200 字
前端本地优先

提问先过本地页面索引与热搜缓存，命中就直接答。只有真正需要查数据的才发请求， 既快又省配额。

前端卡片先出，文字后到

后端不返回流式响应（云函数对长连接支持不稳定），改为先渲染数据卡片，再做逐字动画。 用户感觉是"边说边出结果"，实际是一次性返回。

前端会话令牌自持有

令牌存本地，用账号密码换取并自动续期。请求体里只有问题与历史， 不带任何账号或租户字段。

后端零第三方依赖

编排层不安装任何 npm 包，用运行时内置的请求能力直连模型 API。 部署包极小、冷启动快、供应链风险低。

08 · 与迁移的关系
迁云时这一块要改什么

AI 助手是整套系统里迁移成本最低的部分之一，因为它的边界划得很干净。

部分现状改动说明
编排层 云函数 ai-gateway 并入服务 逻辑不动，只是从独立云函数变成主服务里的一组路由
模型调用 DeepSeek 官方 API 零改动 公网 HTTPS 调用，与云厂商无关；只需确认出口 IP 是否需报备
工具层 走现业务库 随库迁移 工具查的就是业务表，数据库搬完即可用
令牌鉴权 自建 ai_sessions 零改动 本来就不依赖云开发的匿名登录，反而比主系统更"可迁移"
前端入口 HTTP 网关地址 改地址 一处常量，随主系统域名一起换
一个值得强调的点：这套设计当初就是为了「不依赖云厂商能力」而做的 —— 自己签发令牌、自己管配额、直连模型 API、不建向量库。 现在正好验证了它的价值：整个 AI 模块迁云几乎不用改代码。
