实施方案

跨云迁移实施方案

将现有运行于腾讯云 CloudBase 的车队运输管理系统，迁移至标准云架构。 本文给出天翼云与阿里云两套并行方案，对比其技术能力与落地差异， 并就该场景下计算形态选型与服务拆分方式给出明确结论。

版本 v1.0 日期 2026-11-24 规模基线 2,000 台车 / 20 客户 迁移对象 Web 后台 + 30 个云函数 + 30 张表
00

决策摘要

四句话讲完这次迁移的判断。

结论一
两家云厂商的改造清单 90% 相同
只在产品名称、对象存储签名方式、备案入口上不同。因此架构应按「云厂商中立」设计，把差异收敛到一个适配层。
结论二
天翼云只能用 ECS，阿里云可 ECS 也可 FC
天翼云未见对等的托管函数计算产品，形态上没有选择；阿里云两条路都通，但本场景应选 ECS。
结论三
采用 ECS + RDS 形态
单台 4C8G 承载 Web 服务、采集器与定时任务，数据库用托管 PostgreSQL。理由见第 04 节。
结论四
先做模块化单体，不做微服务
30 个云函数重组为 9 个业务模块，跑在同一进程内；按运行特征拆 3 类进程，保留将来拆服务的边界。

02

方案 A · 天翼云

形态上唯一的选择：ECS 承载全部计算，数据库用托管 PostgreSQL 或单机自建。

方案 A

天翼云 · ECS + 关系数据库 PostgreSQL

标准 IaaS 架构，无 Serverless 组件
适配度 高
资源构成（一期 2,000 台车）
弹性云主机4C8G × 1 云硬盘40G + 200G PostgreSQL2C4G / 100G 对象存储 ZOS50G 弹性 IP5M 带宽 VPC + 安全组数据库不对公网 SSL 证书DV 单域名
架构要点
一台机器承担三类负载：Nginx（托管前端静态包 + 反向代理）、Node API（4 进程，吃满 4 核）、位置采集器（单进程常驻）。 定时任务跑在独立进程中，避免多进程重复触发。
数据库建议单库不分库。PostgreSQL 原生不支持跨库 JOIN，若把业务与位置拆成两个库， 「运单 + 车辆最新位置」这类关联查询将无法直接完成。位置数据单独建表即可，67 次/秒的写入对单库无压力。
成本构成
弹性云主机 4C8G约 313 元/月包年 8.5 折后约 3,193 元/年
云硬盘 40G + 200G约 120 元/月系统盘 + 数据盘
弹性 IP + 5M 带宽约 100 元/月地图瓦片走高德，不占此带宽
关系数据库 2C4G待询价参考 350–600 元/月
对象存储 50G待询价参考 10–20 元/月
合计约 900 – 1,050 元/月年约 1.0 – 1.2 万元
省钱备选
不买托管数据库，在主机上自建 PostgreSQL：月成本可压到 450–500 元。 但需注意——PostgreSQL 吃内存，自建时主机必须升到 8C16G，4C8G 会不够用。 升配后省下的钱抵回去一部分，且失去自动备份与主备切换。

方案 B · 阿里云

两条路都可走，本文两个都列出，并在第 04 节给出取舍依据。

方案 B1

阿里云 · ECS + RDS for PostgreSQL

与方案 A 形态一致，仅产品名与存储接口不同
推荐
资源构成（一期 2,000 台车）
ECS4C8G × 1 ESSD 云盘40G + 200G RDS PostgreSQL2C4G / 100G 对象存储 OSS50G CDN静态资源必配 SLB二期再加
与方案 A 的唯一差异
对象存储签名算法不同（OSS 与 ZOS 各自的鉴权机制），需重写签发函数。这是唯一需要改代码的地方。 业务表只存键名与大小、不存访问地址，因此历史数据无需回填。
CDN 必须配。前端首屏 gzip 后约 625KB，5M 带宽约 625KB/s， 十余人同时打开首页就会打满。静态资源走 CDN 后，带宽只承载 API 请求。

方案 B2

阿里云 · 函数计算 FC + RDS + OSS

保留现有 Serverless 形态，30 个函数分别迁到 FC
不推荐
做法
30 个云函数逐个迁到 FC：改入口函数名、改事件参数结构、把数据库客户端换成 pg 连接池， 再配置 HTTP 触发器和定时触发器。业务逻辑基本不动。
为什么最终没选它
连接数不可控是决定性因素。FC 的实例数由流量自动伸缩， 每个实例各持一条数据库连接——并发一涨，连接数就成倍增长，托管数据库的连接上限容易被瞬间打满， 且难以提前预估容量。而 ECS 的进程数完全由自己决定，连接总数可以精确控制。
位置采集是常驻轮询任务，需要进程长期存活。函数计算的单次执行有时长上限，无法承担这类任务， 无论如何都要额外准备一台主机——既然主机已经在，不如把业务接口一并放上去。
04

ECS 与函数计算 FC 对比

两张都是计算服务，但运维模型、计费模型、连接模型完全不同。下表按对本系统的影响排序。

维度 ECS 常驻服务（推荐） 函数计算 FC 说明
数据库连接 进程数 × 池上限，可精确控制 实例数 × 1，随流量放大 本系统最关键的差异，直接决定容量是否可预估
部署单元 1 个服务（4 进程） 30 个函数，各自打包上线 改一处逻辑只部署一次，而不是三十次
本地调试 与线上完全一致 依赖云端日志与模拟器 线上问题能否在本地复现，直接影响排查效率
冷启动 无 有，依赖包越大越慢 本系统有单个函数的依赖包达 42MB
长任务 / 常驻 支持 单次执行有时长上限 位置采集是常驻轮询，FC 无法承担
闲置成本 固定（约 300–400 元/月） 零（无调用不计费） 本系统是稳定持续负载，非突发型，FC 的优势用不上
水平扩展 手动升配或加机器 自动扩实例 二期 2 万台时可再评估
运维负担 需管系统、进程、日志 平台托管 用容器化可大幅抵消这部分负担
厂商绑定 弱，换云只换机器 强，FC 为专有形态 本次迁移由合规驱动，未来可能再迁一次
结论：选 ECS。 三个理由按权重排序——连接数可精确控制（容量可预估）、能跑常驻采集任务（FC 硬性做不到）、 不被单一厂商锁定（下次换云只换机器、不改代码）。 至于闲置成本，本系统是稳定持续负载，函数的按量优势发挥不出来。
05

推荐架构：ECS + RDS

一期单机全包，二期再上负载均衡与多节点。以下是最终落地形态。

目标

单台 ECS 4C8G 全包 + RDS PostgreSQL + 对象存储 + CDN

计算与存储分离，静态资源走 CDN，数据库独立托管
一期
机器上的进程划分
进程实例数连接数职责
Nginx10托管前端静态包、反向代理、HTTPS 卸载
Node API44 × 15 = 60承载 9 个业务模块的全部接口
位置采集器15定时拉取车辆位置，批量入库
定时任务15证照巡检、行为统计等周期任务
合计—约 70托管数据库连接上限为数百量级，余量充足
三条必须守住的实现约束
连接池必须单例。30 个模块共用同一个池，由 db.js 统一导出。 若每个模块各自建池，4 进程 × 30 个池 × 默认上限，连接数会瞬间击穿数据库。
定时任务不能写在 API 的启动逻辑里。多进程模式下，每个进程都会执行一次初始化， 导致采集重复、统计重复、通知重复发送。必须单独起进程，或指定仅 0 号实例启用。
时区必须显式声明。容器与部分运行环境默认为 UTC， 而统计口径依赖「当天」。差 8 小时不会报错，只会让报表数字悄悄错掉。
部署方式演进
一期裸机 + 进程管理器 二期容器化 + 负载均衡 三期按需拆分独立服务
建议容器化与本次迁移合并做。迁移本身就要重写部署方式，此时把镜像一并写好不额外增加工期； 而容器镜像不依赖云厂商，下次换云只需拉镜像、启动、切域名，迁云成本从两天降到半小时。
06

服务拆分与组织

这一节分两步讲：现在的问题具体在哪（有数据可查的位置，不是笼统说"耦合"）， 以及改成什么样、怎么拆。结论先说——不拆微服务，但结构必须理顺。

6.1

现状：四个具体病灶

每条都能在代码里指出位置
病灶实测证据带来的代价
巨型文件 30 个函数共 15,003 行；运单动作单文件 1,942 行，里面塞了 9 类动作、23 处分支判断 改一个动作要在两千行里找位置，也没法单独测试
逻辑重复 同一个校验函数 assertModule 在校验逻辑完全相同地被复制了 5 份；租户过滤条件在运单 4 个函数里出现 100 次 修一个权限漏洞要改 5 处，漏掉任何一处就是安全缺口
无共享层 函数目录下没有公共目录，任何复用只能复制粘贴 重复是结构性的，不是疏忽——想复用也没有地方放
部署碎片化 30 个独立部署单元，各自打包、各自配环境变量 改一处跨函数逻辑要部署多次，容易漏
把四个病灶串起来看：30 个函数形式上已经是微服务——独立部署、独立进程、跨函数走 HTTP， 但它们共享同一套表结构。这属于「分布式单体」：承担了分布式的全部复杂度，却没得到微服务的好处 （独立发布的价值只对多团队成立，而这里只有一两个人）。
顺带发现一个隐患：那份复制了五遍的校验函数，开头写的是 if (!account) return true—— 没传账号时直接放行。收口到共享层后可以顺手收紧为默认拒绝，因为那时只有一处需要改。

6.6

三条依赖规则

守住这三条，将来拆微服务只是替换传输层
① 模块之间只能调用对方的 service.js，禁止直接查对方的表。 比如费用模块要知道运单状态，就调 waybill.getStatus(id)，不写 select from waybills。
② 模块内部结构不对外暴露。repo.js、handlers/、router.js 都是模块私有，其他模块不可引用。
③ 需要跨模块感知状态变化时，发内部事件，而不是直接读取对方数据。 这是低成本预留的关键——在单体内用进程内事件把「运单状态变更」广播出去，费用模块订阅事件； 将来真要拆分，把进程内事件换成消息队列即可，业务代码不用动。

2把确有独立需求的部分拆出去（采集器、AI 网关）出现独立扩缩容或资源隔离需求1–2 周
3完整微服务 + 容器编排团队 5 人以上，或单服务并发过千2–3 个月
真正的门槛不在技术，在数据库。微服务的铁律是「每个服务独占自己的库」， 而本系统中运单、费用、车辆是高度交叉查询的：运单列表要显示车辆档案与费用合计， 费用审批要判断运单状态，里程统计要读运单的行驶记录。拆开之后这些 JOIN 全部消失， 只能改成多次接口调用再组合、或做数据冗余、或引入补偿事务——这一步没有取巧办法。
07

实施计划

按依赖顺序排列。阶段一与阶段二可并行，阶段三必须在阶段二完成后启动。

总工期约 3 周（纯开发），不含备案等待（7–20 工作日）与小程序审核（1–7 天）。 建议把「令牌鉴权改造」与「上云改造」合并为一次，避免同一批代码改两遍。
P1

资源与合规准备并行 · 5–20 工作日

开通云主机、托管数据库、对象存储、带宽、证书；在目标云完成接入备案（原备案不能平移，备案期间旧环境不能停）； 小程序后台配置新的服务器域名（需 HTTPS 且已备案）。
P2

代码改造1.5–2 周

数据访问层重写（工作量最大）：前端数十处直连数据库的调用改为走自建接口，引入单例连接池。
令牌鉴权：替换云开发的匿名登录机制，建立自建令牌与会话表。
云函数合并：30 个函数重组为 9 个模块，入口改为路由，业务逻辑不动。
对象存储适配：重写签名函数，按目标云切换。
P3

数据迁移与验证0.5–1 天

用 pg_dump 完整导出（含结构与序列状态），导入目标库。
导完立即验证两件事：序列当前值是否正确（否则新插入会撞主键）、授权语句是否需按目标库重写。 另需核对行数与关键表的抽样数据。
P4

并行运行与灰度切换3–5 天

新旧环境并行，用真实账号验收主要链路：登录、运单列表、运单动作、费用上报与审批、全图位置、报表导出。
切换时先改域名解析，观察错误率与响应时间，确认稳定后再停旧环境。
P5

收尾与观测持续

配置监控告警（进程存活、接口错误率、数据库连接数、磁盘）；建立每日数据库备份并定期验证可恢复； 旧环境保留一个月作为回退通道。
08

风险与应对

按发生概率与影响排序。前三条属于「不提前处理就会出事故」的级别。

风险 概率 影响 应对
备案窗口期 高 高 接入备案需 7–20 工作日，期间旧环境必须保持可用。提前启动，不要等到开发完成才提交。
小程序提审 高 中 更换合法域名后须重新提交审核，审核期不能发布。安排在业务低峰期，且准备回滚方案。
连接数击穿 中 高 连接池必须单例；按「进程数 × 池上限」计算总量并留余量；上线前压测峰值并发。
时区错位 中 中 显式声明时区，上线后实测一次定时任务触发时间与一条统计结果。该问题不报错，只让数字错。
定时任务重复执行 中 中 多进程模式下若定时逻辑写在启动代码里，会按进程数重复执行。单独起进程或限定单实例启用。
数据迁移遗漏 低 高 完整导出（结构 + 数据 + 序列）；导入后核对行数与序列当前值；保留导出文件至少一个月。
成本预期偏差 中 中 当前为托管型按量形态，迁至独立资源后成本上升约 50 倍属形态差异，需在提报时主动说明，避免上线后产生质疑。
第三方接口白名单 低 中 车联网与 AI 接口若限制来源 IP，需提前把新环境的出口 IP 报备给对方。
